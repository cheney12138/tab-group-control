# 重新打开的写操作归 worker: 弹窗只发消息, 不自己干活

「重新打开」归档卡的动作(建标签 → 归入原生分组 → 焚卡)从弹窗挪进 background service worker。弹窗侧只剩三件事:发一条 `reopen-archive` 消息、拿回结果、收场(刷列表 / 收面板 / 还焦点)。

## 病例(2026-11): 点「重新打开」, 弹窗当场没了

弹窗模式下点「重新打开」, 归档卡确实被重新打开了, 但**用户眼前的弹窗消失了** —— 收场那几步(toast / 刷新 / 收面板 / 高亮恢复的行)全都没发生。

上一轮修的是**独立窗口**(`popup.html?win=1`)那条路:那里是我们自己的 `window.close()` 决定的, 加一道失焦宽限期(`autoCloseHoldUntil`)就够。弹窗模式不一样:

- 贴图标弹出的 action popup 是浏览器窗口上的一层浮层, **失焦即被 Chrome 关掉**, 没有任何 JS 能拦;
- 建标签 / 归组会让浏览器窗口重新拿到焦点 —— 开关不在我们手里;
- 被关掉的是**整个文档连同它的 JS**:串行 `await chrome.tabs.create(...)` 链会当场蒸发在中间 —— 标签建了一半、归档卡没焚、用户什么也没看到。

所以"在弹窗里把动作做完"这条路的前提本身就不成立。修法不是让它别关, 而是**别把数据押在它身上**。

## 决定

### 1. 写操作归 worker

`reopen-archive` 一条消息, worker 里把整件事做完:建标签(落点窗口由弹窗侧解析后传进来)→ 走同一条 `enqueueGroupOp` 串行队列归组 → 按 ADR-0001 的口径焚卡(部分失败只核销已打开的那部分)。弹窗中途死掉也不影响数据落地, 也不会停在"一半"的状态。

### 2. 弹窗被关掉就把它唤回来

worker 跑完先查 `chrome.runtime.getContexts({ contextTypes: ['POPUP'] })`:

- 弹窗还活着 ⇒ 什么都不做(收场 / 提示由发起它的那个弹窗自己完成);
- 弹窗没了 ⇒ 把恢复结果塞进 `chrome.storage.session`, 再 `chrome.action.openPopup()` 把它唤回来。

新弹窗是全新文档, 首屏从 session 里接住那份结果(`consumeReopenHint`):新标签的标题 / 图标不必等页面加载定型, 并且补一条「已重新打开」回报 —— 否则用户看到的就是一个"莫名其妙又回来"的弹窗。

只在**动作发起方是弹窗**时这么做(`fromPanel`):独立窗口面板本来就不受失焦自关影响, 凭空多开一个弹窗只会让人莫名其妙。

## 被否掉的路

- **归档恢复期间阻止失焦关闭**:弹窗的失焦关闭是浏览器行为, 页面里的任何 `blur` 监听 / `preventDefault` 都拦不住 —— 这条路根本不存在。
- **普通 popup 模式下不关设置面板, 只切回分组视图**:设置面板是覆盖层, "回到分组视图"就是收起它;收面板这个动作与弹窗被不被关掉无关, 换汤不换药。
- **只在弹窗里加宽限期**:独立窗口那条路已经这么做了, 但弹窗模式没有可延长的东西 —— 关它的是浏览器, 不是我们。

## 自测

- `probes/tgs-archive-popup.mjs`(15/15):真 popup(CDP 直连 Target)+ 动作发出后立刻 `window.close()` 模拟"按 Chrome 的方式被带走" —— 标签照样建齐归组、卡照样焚、弹窗被唤回且落在恢复的分组上(分组展开, 不被旧的收起记忆压回去)、补一条回报、弹窗活着时不许多开一个。
- `probes/tgs-archive-restore.mjs`(12/12)、`probes/tgs-archive-live.mjs`(12/12):收场顺序 / 落点窗口 / 独立窗口不失焦自关, 口径不变。
