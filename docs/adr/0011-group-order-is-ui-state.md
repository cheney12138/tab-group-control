# 分组分区序是界面状态,不是数据的投影

浏览视图里分区的先后顺序,由一份**记账本**(`core/group-order.js`)掌管;数据序(`lastAccessed`)只在某个分区**第一次出现**时决定它插在哪。

## 病根

分区序过去完全从数据推出来(`render.js`):先按组内最新标签的 `lastAccessed` 倒序切分区,再把"含当前激活标签"的分区钉到第一位。三条裂缝都由这个推导产生,且都在**批量关闭 → 撤销**这条路上同时爆掉:

1. **某组的最新标签被关 ⇒ 该组时间戳降级 ⇒ 掉到后面。** 用户关的是"几个标签",看见的却是"剩下的组换了位置"。
2. **组被清空 ⇒ 分区整块消失 ⇒ 撤销重建时落点是随机的。** Chrome 会给新标签 `lastAccessed = now`,旧版 `undo.js` 用 `safeLastAccessed` 把它压到"不超过本组已有最大值 / 不超过全场第一"来保住组的相对排位 —— 压一条够用,压一批两面崩:同组多条一起恢复时全被压到同一个上限值(组内名次全乱),整组被清空时只剩"不超过全场第一"这条(重建的组一路被压到列表最底部)。
3. **关掉激活标签后 Chrome 换了激活标签 ⇒ 钉顶规则把另一个组钉到第一位。** 这一条每次重渲染都会重新执行,于是"关完一刷新,列表整体重排"。

三条叠加起来的用户感受是一句话:关了几个标签,列表跳了,撤销的展开动画在别的地方演(`docs/motion.md` 里那条"删除/撤销是一段倒放"因此读不出来)。

## 决定

一次 popup 会话内,**分区的先后顺序是界面状态**:

- 记账本按 `key = ${windowId}|${groupKey(group)}` 记座次。键**不含** chrome 的 `groupId` —— 组被清空后 Chrome 会回收它,重建时 id 是全新的,但组名+颜色还在。
- 已在记账本里的分区按记账本的名次排;新分区(刚建的组 / 刚改名的组)贴住数据序里的前一格(`prev + 0.5`)落位 —— 新组不会因为"不认识"而被甩到列表末尾。
- 被清空的组留座 `ORDER_TTL_MS = 12s`(撤销窗口 6s 的两倍)。撤销重建的同名同色组因此回得到原来的名次;宽限期过了、且一直没再出现才忘掉。
- 目标含激活标签的批量关闭会连 popup 一起关掉(ADR-0006),撤销发生在新 popup 里 —— 那边首帧只看得到"剩下的组",所以**记账本要跟撤销凭证一起落 `chrome.storage.session`**(`persistUndoBatch` 的 `order`),`restoreUndoBatch` 时先播种再让撤销可点。
- 分组改名/改色时座位跟着搬(`remapGroupOrder`,与 `remapGroupKey` 搬收起记忆同理)。

## Consequences

- `render.js` 的"当前组钉顶"退化成**首帧播种规则**:它决定的只是这次 popup 会话开局时的名次,之后不再重排。重启/换机后 `lastAccessed` 全部近似相等的老问题依旧被它兜住(见 2026-10-14 病例)。
- `undo.js` 的 `safeLastAccessed` 整套删除,恢复的标签带回**原始** `lastAccessed`。组内名次与关闭前逐行对齐,组的相对时间也原样复原 —— 分区序不再依赖它。
- 新分区落在哪里取决于数据序,所以"同一 popup 会话里新建一个组"仍然会出现在数据说它该在的地方(组内最新标签是刚操作出来的,通常就在顶部附近);不需要额外的"新建组插哪"规则。
- 记账本是内存态。popup 关掉后重开(没有撤销凭证)就按数据序重新播种 —— 与改动前一致,不引入跨会话的排序持久化。
- 同窗口允许有两个同名同色的组(Chrome 不禁止),身份键会撞车;撞车的第二个起加 `#n` 序号,否则 `Map` 会把一个分区整块吞掉、那一组的标签从列表里消失。
